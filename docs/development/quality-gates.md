# Offline quality gates

`.github/workflows/quality.yml` runs on pull requests, pushes to `main`/`master`, and manual dispatch. Its two checks are **Offline Python tests** and **Frontend tests, types, lint and build**. Require these checks in the repository's branch protection settings before relying on them as merge gates; adding the workflow does not change those settings automatically.

The Python job uses the repository's Python version and `uv.lock`, with `uv sync --locked --group dev`. It installs the base application and test dependencies without optional MIDAS, alignment or online-service extras. A stale lockfile fails installation instead of being rewritten. The existing Linux dependency graph includes large Torch/CUDA wheels through base dependencies; this job does not silently remove them or substitute another numerical environment.

Tests run with APEXA's data/offline policy, offline Hugging Face settings, no model credentials, no configured writable/stoppable EPICS devices, and an isolated temporary session directory. The regression suite uses stubbed model/control/engine calls, in-process HTTP transports, and synthetic fixtures. Dependency installation accesses package registries; this is not a claim that the whole runner has network access disabled. Do not add real provider, SSH, acquisition or hardware tests to this job.

The suite reports skip reasons with `-ra` and retains JUnit results for 14 days. Tests requiring an external MIDAS package/manual checkout, a synthesis native environment, or macOS `sandbox-exec` may be skipped when those capabilities are absent. Missing required base dependencies or portable fixtures must fail rather than be converted into blanket skips. These checks do not qualify MIDAS/GSAS-II/TomoPy numerical accuracy, GPU equivalence or a commissioned motor/interlock configuration.

The frontend job installs `frontend/package-lock.json` using `npm ci`, then runs Node tests, TypeScript, ESLint and Vite. Node 24 supplies the native TypeScript and module-hook APIs used by the existing tests. The production build goes to runner temporary storage; CI does not update or deploy the tracked `frontend/dist` directory. Node tests exercise state, transport and static markup, not browser performance or accessibility.

The optional real-browser synthetic runner and its measured scope are documented in [Frontend performance](../FRONTEND_PERFORMANCE.md). It is not included in the hosted workflow because Playwright/browser installation is currently external tooling rather than a locked application test dependency.

The workflow controls have focused transport, controller and markup tests in the standard Node suite. They exercise captured gate/revision approval, duplicate clicks, lost-response retries with the same request ID, session isolation, active-only polling, reject-only gates and unresolved cancellation. With the same local Vite and external Playwright/browser setup described above, `node tests/browser-workflows.mjs` exercises the actual review buttons, a stale-window conflict, evidence links, session switching, chat-triggered refresh and API failure display. This runner intercepts API calls with synthetic responses; it does not validate a scientific engine or execute hardware.

Both jobs use GitHub-hosted runners with read-only repository token permissions, disabled checkout credential persistence and pinned action commit IDs. They require no deployment secrets. No release, publication or beamline installation is performed. A first successful hosted run is still needed to validate the Linux installation and runner environment; local test results alone do not establish that hosted outcome.
