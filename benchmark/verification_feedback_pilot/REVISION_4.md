# Internal application-validation check

This is software validation following the completed R3 audit, not a new paper
experiment. Keep the main manuscript and supplement free of software-revision
labels, extra case names and an expanding list of result counts. The paper's
existing relative-motion and reconstruction-correspondence cases remain its
structure. Any later use of the completed safeguard finding should replace or
condense an existing supporting example, with detailed history in the code/data
package. R1–R3 already names unrelated solver routes in the supplement.

Changes: application-owned contract activation before any model request; separate
validation of the original-handoff decision; and factual finalizer summaries
constructed from recorded numerical evidence. Original agent proposals remain
available for audit. Free-form chat claims remain outside this guarantee.

Validate the same four already-qualified handoffs once each, with two slots:
valid scale and valid restriction first, then faulty scale and faulty restriction.
Use GPT-OSS-120B and the same solver, context, per-attempt request/time allowances
and CPU allocation. Do not regenerate fixtures, alter R2/R3 records, replace
failures, or pool the new attempts into their outcomes.

Admission requires local and deployed production-path tests, source/context hash
checks and a fresh native session. Verify automatic activation from the actual
client receipt rather than a redundant boolean echoed by the model. Freeze the
exact code/configuration before admission. Keep all failures and stop admission on
startup or provider failures as before.

Inspect activation in every attempt, original versus final decisions, saved schema,
actual frames/model/pitch, artifact and receipt hashes, and consistency of the
authoritative summary with numerical outputs. A successful application-generated
report is a system result; separately retain any unsupported model proposals or
chat claims. This check provides no new harness ranking or unseen-data claim.
